# 프롬프트 점검 가이드

Claude Code에 작업을 지시하기 전에 프롬프트 품질을 점검하는 기준이다.
`/prompt-check <프롬프트>` 명령이 이 문서를 기준으로 채점한다.

## 1. 점검 기준 (각 10점 만점)

| 항목 | 10점 기준 | 흔한 감점 요인 |
|------|-----------|----------------|
| 토큰 효율 | 작업에 필요한 정보만 있고 중복·장황한 배경이 없음 | 긴 로그/코드 붙여넣기, 같은 요구 반복, 인사말·사족 |
| 명확성 | 해석이 하나로만 가능하고 대상(파일·함수·범위)이 특정됨 | 모호어 사용, 대명사("그거", "저번 것"), 대상 파일 미지정 |
| 완결성 | 목표·제약·완료 기준·출력 형식 4요소가 모두 있음 | 완료 기준 없음, 출력 형식 없음, 건드리면 안 되는 범위 미기재 |
| 구조 | 목표 → 배경 → 제약 → 완료 기준 → 출력 형식 순으로 구분됨 | 요구사항이 문장 속에 섞임, 목록화 안 됨 |

### 완결성 4요소

- **목표**: 무엇을 달성하는가 (한 문장)
- **제약**: 하지 말아야 할 것, 수정 금지 파일, 사용 라이브러리 제한
- **완료 기준**: 무엇이 확인되면 끝인가 (테스트 통과, 파일 생성 등 검증 가능한 조건)
- **출력 형식**: 결과를 어떤 형태로 받을 것인가 (표, 코드 블록, N줄 요약 등)

### 점수 해석

- 9~10점: 그대로 실행
- 8점: 실행 가능, 사소한 보완 권장
- 8점 미만: 보완 후 실행

## 2. 모호어 목록과 대체 표현

| 모호어 | 문제 | 대체 표현 예시 |
|--------|------|----------------|
| 적당히 | 기준 없음 | "함수당 30줄 이하로" |
| 깔끔하게 | 주관적 | "ESLint 경고 0개, 중복 코드 제거" |
| 잘 | 기준 없음 | "기존 테스트 전부 통과하도록" |
| 최적화해줘 | 대상 지표 불명 | "응답 시간을 200ms 이하로" / "메모리 사용량 절반으로" |
| 개선해줘 | 방향 불명 | "에러 메시지에 요청 ID를 포함하도록" |
| 간단하게 | 범위 불명 | "3줄 이내로" / "외부 의존성 없이" |
| 빠르게 | 속도인지 작업 시간인지 불명 | "O(n) 이하로" / "변경 파일 1개로" |
| 좀, 약간 | 양 불명 | "재시도 횟수를 3회로" |
| 필요하면 | 판단 기준 불명 | "입력이 null이면 기본값 0 사용" |
| 등, 기타 | 범위 불명 | 대상을 모두 나열 |
| 그거, 저번 것 | 대상 불명 | 파일 경로·함수명 명시 (`src/client.ts:fetchPr`) |
| 알아서 | 결정 위임 범위 불명 | "A와 B 중 선택하고 이유를 1줄로" |

## 3. 기법 선택표

| 작업 유형 | 기법 | 적용 예 |
|-----------|------|---------|
| 단순 작업 (수정 범위가 명확) | 직접 지시 | 이름 변경, 설정값 수정, 문서 추가 |
| 순차 추론 (원인 추적) | CoT (Chain of Thought) | 디버깅, 성능 병목 분석 |
| 대안 비교 (정답이 여러 개) | ToT (Tree of Thoughts) | 설계, 라이브러리 선택, 리팩터링 방향 |

### 3.1 직접 지시 예시

```
목표: src/config.ts의 DEFAULT_TIMEOUT을 5000에서 10000으로 변경
제약: 다른 파일은 수정하지 마
완료 기준: npm test 통과
출력: 변경한 줄 diff만
```

### 3.2 CoT 예시 (디버깅)

```
목표: PR 목록 조회 시 401 에러 원인 찾기
배경: 에러 로그는 logs/error.log 참고
절차: 다음 순서로 단계별로 확인하고 각 단계 결과를 1줄씩 기록해
  1) 인증 헤더 생성 코드 확인
  2) 환경변수 로딩 확인
  3) 실제 요청 헤더 확인
제약: 원인 확정 전에는 코드 수정 금지
완료 기준: 원인 1개 특정 + 근거 코드 위치
출력: 단계별 확인 결과 표 + 원인 + 수정안
```

### 3.3 ToT 예시 (설계)

```
목표: 웹훅 이벤트 처리 방식 결정
절차:
  1) 대안 3개 제시 (동기 처리 / 인메모리 큐 / 외부 큐)
  2) 각 대안을 복잡도·신뢰성·운영 비용 기준으로 평가
  3) 가장 약한 대안은 버리고 남은 2개를 비교해 1개 추천
제약: 새 인프라 도입은 비용 근거 필요
완료 기준: 추천안 1개 + 선택 이유
출력: 비교 표 + 추천 이유 3줄 이내
```

## 4. 토큰 절약 규칙

1. **긴 로그는 파일 경로로 대체**: 20줄 넘는 로그·스택트레이스는 붙여넣지 말고 경로만 준다.
   - 나쁨: 로그 300줄 붙여넣기
   - 좋음: "`logs/error.log` 마지막 50줄 확인해"
2. **프롬프트당 목표 1개**: 목표가 여러 개면 프롬프트를 나눈다.
   - 나쁨: "버그 고치고, 테스트 추가하고, README도 정리해"
   - 좋음: 버그 수정 → (완료 후) 테스트 추가 → (완료 후) README 정리
3. **중복 배경 삭제**: CLAUDE.md·이전 대화에 이미 있는 내용은 반복하지 않는다.
   - 나쁨: "이 프로젝트는 TypeScript로 된 Bitbucket MCP 서버인데..."
   - 좋음: 바로 목표부터 시작
4. **코드는 위치로 지목**: 코드 전체 대신 `파일:줄` 또는 함수명을 준다.
5. **출력 길이 제한**: "N줄 이내", "표로만" 등으로 응답 토큰도 줄인다.

## 5. 점검 체크리스트

- [ ] 목표가 한 문장이고 1개인가
- [ ] 모호어가 없는가 (2장 목록 대조)
- [ ] 대상 파일·함수가 특정되었는가
- [ ] 제약(수정 금지 범위)이 있는가
- [ ] 완료 기준이 검증 가능한가
- [ ] 출력 형식이 지정되었는가
- [ ] 작업 유형에 맞는 기법을 썼는가 (3장)
- [ ] 긴 로그·중복 배경이 없는가 (4장)
